# Text: первый исполняемый этап

Принятый контракт и реализация от 27 октября 2026.

## Контракт

`&str` — неизменяемое представление корректного UTF-8: адрес, длина **в байтах**,
область памяти. Оно допускает Flash и SRAM без пользовательских `<memory M>`.
Размещение не означает время жизни или владение. Программа должна работать и тогда,
когда размещение выбирается во время выполнения. Специализация — оптимизация,
а не условие корректности.

Литералы размещаются во Flash, без копии содержимого в SRAM и без добавленного NUL.
Поддерживаются escapes `\n`, `\r`, `\t`, `\0`, `\\`, `\"`; прочие escapes и физические
переносы внутри литерала отклоняются. Исходники читаются как UTF-8. Нулевой байт
внутри текста не завершает его. Текущий предел длины — 65535 байтов; фактическая
вместимость MCU дополнительно проверяется по связанному ELF.

## Доступный исходный код

```helium
import extension std::uart::UartText;
device debug = UART0 { baud: 38400, mode: TX, }

fn print_n(device uart: UartTx, s: &str, n: u16) {
    var i: u16 = 0;
    while i < n {
        uart.println(s);
        i = i + 1;
    }
}
setup { print_n(debug, "Привет", 2); }
loop {}
```

Поддержаны параметры `&str`, локальные инициализированные ссылки, присваивание
и условный выбор ссылок, передача через функции и модули. Присваивание копирует
представление, не содержимое. Возврат ссылки и глобальное хранение отклоняются.
Все доступные из исходника источники текста пока являются бессрочными литералами;
это не реализация общего borrow checker.

Методы именованной ссылки:

* `s.len(): u16` — длина в байтах;
* `s.byte_or(index: u16, fallback: u8): u8` — байт или явно заданный fallback,
  если индекс вне диапазона. Оба аргумента вычисляются обычным образом до операции.
  Проверка выполняется до чтения памяти, включая пустую строку и индекс 65535.

`byte_or` позволяет написать безопасный байтовый цикл, не выбирая преждевременно
политику panic/trap для общей индексации массивов. Индексации символов, строковых
операторов и цепочек методов пока нет.

`UartText.print`, `println` и `newline` реализованы на Helium в `lib/std/uart.he`.
`println` добавляет LF (10). В UART не добавлено новых аппаратных примитивов.
Эффекты выводятся через обычные вызовы: blocking-warning в ISR и защита совместного
доступа к UART сохраняются. Произвольные байты не могут стать `&str` через cast.

## IR, LLVM и границы первого этапа (ab27f17)

Этот раздел и исходные измерения ниже описывают первый этап. Явная специализация
реализована следующим этапом: [TEXT_SPECIALIZATION.md](TEXT_SPECIALIZATION.md).

IR содержит `Type::Text`, `TextLiteral`, `TextLen`, `TextByteOr`. Verifier проверяет
типы, длину и запрещает конструировать текст через скалярную `Const` или `Widen`.
IR-интерпретатор поддерживает байтовые операции; UART по-прежнему проверяется
машинным симулятором.

Внутреннее представление LLVM для ATmega328P — `{ i16, i16, i8 }`: адрес, длина,
признак (1 — Flash, 0 — SRAM). Это не обещание внешнего ABI или конкретного
регистрового calling convention. Физическую передачу/размещение определяет LLVM.
Чтение Flash использует `ptr addrspace(1)`, SRAM — `ptr`. Строки дедуплицируются
по содержимому и размещению. SRAM-хранилища IR неизменяемы и тоже содержат UTF-8.

Неспециализированная функция получает все три поля ссылки. Helper чтения сначала
проверяет длину, затем выбирает область. LLVM встраивает этот небольшой helper,
может распространять известное размещение и устранять ненужную ветвь. В текущем
компиляторе **нет отдельного обязательного прохода клонирования всех функций
на Flash/SRAM-варианты**. Не гарантируются ни три отдельных функции print_n,
ни вынесение выбора области за оба цикла. Для неизвестного размещения проверка
может оставаться в байтовом цикле. Эта граница явно отделена от корректности.

## Тестовая матрица

`tests/text.rs` проверяет исходник, межмодульную передачу/ISR effects, IR verifier,
интерпретатор и машинное выполнение `print_n` в LLVM none/speed/size:

1. Flash: разные литералы, UTF-8, встроенный NUL, пустой текст, n=0 и n=2.
2. SRAM: та же функция, immutable SRAM storage из IR fixture.
3. Выбор Flash/SRAM через реальный volatile GPIO input; обе ветви.
4. Пустое представление и индекс 65535: возврат fallback без чтения вне строки.

SRAM fixture заменяет размещение литерала `RAM` в типизированном IR. Это проверка
реального SRAM-чтения в прошивке, **не** доказательство поддержки исходного
`String`, изменяемого буфера или анализа его lifetime. Все промежуточные LLVM,
assembler, ELF, HEX и отчёты сохраняются в `build/text-tests/llvm-*`.

### Измерения print_n

Первый машинный прогон (ATmega328P, 16 MHz, тестовый export_symbols=true;
Flash в байтах, не оценка из исходника):

| Сценарий | none | speed | size | Статическая SRAM |
| --- | ---: | ---: | ---: | ---: |
| Только Flash, включая UTF-8/NUL/пустую строку | 982 | 1244 | 522 | 1 |
| Только SRAM fixture | 934 | 938 | 468 | 5 |
| Runtime-выбор, выполнена SRAM-ветвь | 992 | 1038 | 492 | 5 |
| Runtime-выбор, выполнена Flash-ветвь | 992 | 1028 | 496 | 5 |

Один байт SRAM в Flash-сценарии принадлежит UART, не литералам. Для SRAM fixture
добавляются данные и выравнивание линкера. Эти числа не включают максимальный стек.
Разные сценарии выводят разный текст; таблица не является чистым измерением цены
одного только признака памяти. Export сохраняет также доступные извне тестовые функции.

В speed LLVM встраивает цепочку setup → print_n → println → print для известных
аргументов: в теле setup нет извлечения полей универсального представления. Это
проверяется автоматически по optimized.ll, отдельно от проверки UART-байтов.
Общий экспортированный print_n остаётся с аргументами `{ i16, i16, i8 }` и `i16 n`;
устройство аргументом не передаётся. В этом варианте извлечение области поднимается
из байтового цикла, но ветвление по ней может оставаться внутри цикла. Поэтому
устранение проверки для известных вызовов подтверждено; однократная диспетчеризация
неизвестного размещения на весь print_n пока не заявляется.

Speed оказался больше size из-за встраивания/развёртывания; размер и скорость
нельзя считать одной целью. Лог с измерениями: `build/text-machine.log`.

## Следующие этапы

Уточнение от 28 октября: **явная специализация реализована**, см.
[контракт и проверки](TEXT_SPECIALIZATION.md). Требование: специализация всей цепочки
вызовов по области памяти. Известный вызов идёт напрямую, неизвестный — через
диспетчер перед специализированным телом. Для ссылки с неизменным размещением
внутри функции выбор должен находиться до циклов, независимо от LLVM. Описанные
выше измерения относятся к исторической реализации `ab27f17`.
При замене ссылки в теле на неизвестный источник требуется отдельный выбор.
Несколько параметров и рост числа специализаций проверены в новом этапе.

* Безопасные ограниченные заимствования SRAM: временный доступ на синхронный вызов,
  проверка конфликтов, включая глобальные имена, helpers и ISR. `&mut` не заменяет
  `noInterrupt`. Сохранение/возврат заимствований и общие lifetimes отдельно.
* Fixed scalar-массивы, временные ссылки/слайсы и исполняемый Clone реализованы
  по ARRAYS.md. Создание текста из SRAM-буфера остаётся следующим этапом.
* Фиксированная ёмкость `std::String<N>` без heap — направление принято к дальнейшей
  проработке; конкретный API, const parameters и failure atomicity ещё проектируются.
* Преобразование внешних байтов в текст только с проверкой UTF-8. Расширенная
  Unicode-обработка отдельно; для UART декодер Unicode не нужен.
* Оптимизация выбора области вне циклов и размер специализаций — измерять отдельно.

Физическая плата не прошивалась. AVR8js наблюдает принятые записи UDR, не приём
другим устройством. Максимальный стек и WCET пока не доказаны.

Проверка первого этапа: 180 тестов в debug и 180 в release, включая все машинные тесты;
fmt/Clippy прошли. Финальный лог — `build/text-full-gate-final.log`.

## Ёмкость форматированного текста: требование к следующему этапу

Автор не должен вручную вычислять UTF-8 размер литералов. При проектировании
форматирования предусмотреть помощь в оценке/проверке требуемой байтовой ёмкости:
точный размер констант, верхнюю границу при известных ограничениях аргументов,
проверяемую операцию при неизвестном размере. Конкретные API и политика изменения
назначения при ошибке ещё не утверждены. Для пользовательских форматтеров нельзя
предполагать чистоту или неизменность данных при двух проходах без контракта.
Динамически растущие строки — отдельно; рост требует памяти и может завершиться
неудачей. Потоковый вывод остаётся вариантом без промежуточного буфера.

В обсуждении ссылок различать стабильность адреса, границ/длины, корректность UTF-8
и обещание неизменности содержимого. Фиксированная ёмкость сама по себе не доказывает
все эти свойства. Принято: пока читающее заимствование используется, изменение
данных через другое имя запрещено, включая код вне ISR. После завершения
заимствования изменение разрешено. Реестр контрактов Copy/Clone и move-анализ
реализованы по [VALUES.md](VALUES.md), F19. Временные заимствования массивов проверяются
по [ARRAYS.md](ARRAYS.md); String и создание &str из SRAM-буфера остаются отдельным этапом.
