# Разрешённые сущности и shared-анализ

`analyze` возвращает единый `AnalyzedProgram`, содержащий AST, SymbolTable и граф
вызовов/ресурсов. Доступ через `statements()`, `symbols()`, `shared_analysis()` только
для чтения. Отдельной совместимой ветки, возвращающей один AST, нет.

## Идентификаторы

- SymbolId обозначает объявление: global/local/parameter/function/pin/timer.
- Использования имён, левые стороны присваиваний и вызовы сохраняют SymbolId.
- Объявления функций собираются заранее; остальные имена разрешаются по существующим
  правилам видимости. Запрет затенения сохранён; соседние локальные области имеют
  независимые символы даже при одинаковом написании имени.
- SymbolTable хранит имя, тип/сигнатуру, место объявления и тело-владельца локальных
  сущностей. Номера детерминированы для одного исходника и живут только в его анализе.
- IR FunctionId/LocalId/GlobalId/ValueId остаются самостоятельными идентификаторами.
  Lowering отображает SymbolId в IR-хранилища/функции и не разрешает имена повторно.

Парсер оставляет поля symbol пустыми. Успешный анализ разрешает все употребления
имён и объявления, в том числе в недостижимом исходнике. Ошибочный исходник не
передаётся в построение shared-графа или IR.

## Ресурсы и контексты

`ResourceId::GlobalMemory(SymbolId)` обозначает общую переменную;
`ResourceId::GpioPort(PortId)` — общий ресурс порта. Конкретные пины имеют разные
SymbolId, но один PortId при совпадении порта. Строковые псевдоимена вроде `$portB`
больше не служат идентификаторами ресурсов.

Сохраняются виды обращений: чтение/запись памяти, чтение/запись пина, настройка пина.
Основание защиты хранится отдельно: noInterrupt-блок, контракт функции, setup,
инициализация или тело ISR. Вызов хранит ID функции, исходное место и защиту caller.
Защита caller сама по себе не изменяет контракт обычной вызываемой функции.

BodyId различает Initialization, Setup, MainLoop, Function и Interrupt. Достижимость
из setup, main и ISR вычисляется отдельно. Граф строится один раз и используется
как для диагностики конфликтов, так и для volatile-метаданных IR.

Первый технический этап B1 сохраняет прежнюю консервативную политику ошибок:
setup учитывается вместе с main, проверки распространяются и на невызываемые тела.
Уточнение фаз исполнения выполняется отдельным изменением, с отдельными регрессиями.

Различение типов операций пока не ослабляет правило целого порта. Точное использование
атомарных аппаратных операций — обязательный будущий этап B2a после описания target.
