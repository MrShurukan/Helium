## Вывод

Helium имеет пригодную для дальнейшего развития основу компилятора. Переписывать его заново или возвращаться к собственному AVR backend оснований нет. Но текущий язык ещё не является удобным инструментом для самостоятельного хобби-проекта: большинство реальных задач потребует сначала доработать сам компилятор.

Перспективный продукт — небольшой язык для конкретного класса AVR-устройств, с проверенными библиотеками и простым циклом сборки/прошивки. Наличие синтаксиса, похожего на привычные языки, само по себе эту задачу не решает. Критерий успеха: пользователь меняет логику прибора, не Rust-код компилятора.

## Подтверждённые дефекты

### 1. P2: допустимый глобальный инициализатор ломает verifier Timer1

Место: `src/ir/verify.rs:221`, связанный lowering — `src/ir/lower.rs:223`.

```text
var flag:bool=true;
var value:u8=flag ? 1 : 2;
timer clock=Timer1 {every:1s, interrupt {}}
loop {}
```

Debug `check --cpu-hz 16000000` выдаёт `E_INTERNAL_IR: timer must start exactly once in the startup block`. Release без `--verify-ir` принимает тот же исходник; с этим флагом отвергает.

Причина: тернарное выражение создаёт CFG. Setup и TimerStart оказываются в блоке после слияния, а verifier требует TimerStart именно в исходном entry-блоке. Это несовместимые предположения двух стадий, а не ошибка пользователя. Аналогичный риск относится к short-circuit глобальным инициализаторам.

Исправление: проверять последовательность и достижимость по CFG либо явно выделить фазу инициализации в отдельную функцию. Проверить, что setup предшествует TimerStart на всех путях, старт выполняется один раз и не попадает в повторяемую часть. Не исправлять выключением verifier.

Критерий: ternary/and/or в глобальных инициализаторах с таймером одинаково проходят debug/release, verifier on/off, оптимизации on/off; порядок запуска подтверждён исполнением.

### 2. P2: литералы без контекста проходят support gate и превращаются во внутреннюю ошибку

Места: `src/support.rs:79`, `src/support.rs:148`; преобразование `I::Literal` в I32 в `src/ir/lower.rs`.

```text
loop {if 1 < 2 {}}
```

Результат — `E_INTERNAL_IR` при LLVM emission, без диапазона исходника: emitter обнаруживает неподдерживаемую ширину. Support gate умеет отвергать явно заданные i32/i64, но пропускает промежуточный тип целого литерала. Lowering затем выбирает i32.

Отсутствие машинного i32 задокументировано. Внутренняя ошибка на обычном пользовательском выражении — отдельный дефект. Особенно неудобно, что у операндов сравнения нет переменной, на которой пользователь мог бы поставить аннотацию типа.

Исправление: завершать выбор типов до проверки исполняемого подмножества и выдавать исходную диагностику. Добавление i32 полезно, но не заменяет устранение этой неполноты проверки.

### 3. P2: граница поддерживаемого языка зависит от раннего return

Места: обход выражений в `src/support.rs`, прекращение lowering в `src/ir/lower.rs:500`.

```text
def Led=PortB.0 OUTPUT;
fn f() {Led=true ? INPUT : OUTPUT;}
loop {}
```

Этот исходник отвергается как computed PinMode. Если перед присваиванием добавить `return;`, он проходит `check`. Аналогично `fn f() {return; if 1 < 2 {}} loop {}` принимается, хотя живое сравнение приводит к дефекту №2.

Причина: часть ограничений проверяется только при lowering. Код после return туда не попадает. Воспроизведение не требует включать оптимизацию: проблема уже в построении IR.

Это нарушает заявленное правило SUPPORT/HANDOFF, по которому ограничения применяются и к недостижимому исходнику. Нужен полный source-level support pass с тестами одинаковых конструкций в живом коде, после return и в ветвях.

### 4. P3: README противоречит текущей реализации

`README.md:79` утверждает, что timers и interrupt handlers ещё не реализованы, тогда как ниже описан Timer1. Это небольшой дефект, но для человека, возвращающегося к проекту, он непосредственно мешает определить состояние продукта.

## Что стало существенно лучше

- Старый structural DAG cache больше не является основой генерации. Значения, изменяемые слоты и аппаратные эффекты разделены.
- Есть явный порядок вычисления, short-circuit, проверки диапазонов и wrapping arithmetic. Аппаратные чтения не трактуются как чистые выражения.
- Передача ABI/register allocation в LLVM сокращает объём собственного сложного backend-кода.
- Функции проверяются через собранные сигнатуры; рекурсия отвергается. Есть проверки вызовов с регистрами и стековыми аргументами на машинном коде.
- `noInterrupt` имеет осмысленный контракт восстановления состояния, включая вложенность и return. Volatile и атомарность не смешаны в документации.
- Тесты не ограничены строковыми снимками LLVM: имеются исполнения, разные оптимизации, намеренно испорченный IR и диагностики диапазонов.

Это существенное продвижение относительно старого состояния. Но 105 зелёных тестов доказывают покрытые сценарии, а найденное сочетание глобальной инициализации и таймера показывает нехватку тестов взаимодействия возможностей.

## Архитектурные и продуктовые слабости

### Несколько источников истины о типах и допустимости

AST мутируется семантическим анализом, промежуточные типы живут дальше, support pass повторно обходит исходник, lowering снова решает часть вопросов, emitter ещё раз ограничивает типы. Полезные защитные проверки сами по себе нормальны; проблема в неполном контракте между ними.

Нужно постепенно сделать границу «семантика завершена» явной: выражения имеют конкретные типы, ссылки на разрешённые сущности, все пользовательские ограничения уже проверены. Не обязательно немедленно создавать ещё один большой IR. Начать можно с устранения остаточных literal types и общего механизма обхода выражений.

### Анализ общей памяти чрезмерно связан с глобальным состоянием программы

`shared.rs` хранит имена ресурсов и список вызываемых имён; контекст конкретного вызова не переносится. При текущем запрете shadowing и явных `noInterrupt fn` это работоспособно, но плохо масштабируется на модули, поля и передаваемые ресурсы.

Проверен пример: невызываемая `fn unused():u8 {return x;}` получает E_SHARED_ACCESS, когда ISR пишет x, а loop читает x под защитой. Финальная проверка обходит все тела, а конфликт определяется существованием main/ISR-доступов в программе. Это рассматривается как консервативная политика, не доказанный пропуск защиты. Однако ошибка в невызываемой функции и изменение требований к helper при добавлении таймера ухудшают понятность библиотек.

Перед библиотеками следует определить, что именно обещает функция о shared-ресурсах, отделить setup от конкурентной фазы и перейти от строк к SymbolId/ResourceId. Не обязательно сразу вводить полноценный borrow checker.

### Жизненный цикл и target зашиты в нескольких местах

Номера entry/setup/loop 0/1/2 используются в lowering и verifier. AVR-регистры и vector Timer1 находятся в LLVM emitter, тогда как описание target существует отдельно. На одном MCU это терпимо; перед вторым устройством периферии стоит выделить именованные lifecycle roles и единое описание аппаратных регистров/ресурсов.

Не нужна заранее универсальная система десятков targets. Нужна небольшая граница между операцией языка и конкретной AVR-реализацией.

### До библиотечного языка отсутствуют необходимые возможности

| Потребность | Текущий барьер |
| --- | --- |
| Два одинаковых устройства | Нет структур состояния, массивов и передаваемых Pin |
| Обмен байтами, адрес датчика, CRC | Нет фиксированных буферов и битовых операций; деление также не реализовано |
| Повторное использование драйвера | Нет module/import и полноценного способа параметризовать оборудование |
| 1-Wire и другие временные протоколы | Нет установленного API задержек с проверяемым временным контрактом |
| LCD и отладка | Нет строкового вывода, форматирования и UART-драйвера |
| Длительное измерение времени | Только 8/16-битные машинные целые; нет готовой политики переполнения счётчиков времени |
| Объяснимый расход SRAM | Есть размеры секций, но нет максимума стека с учётом ISR |
| Работа без знания устройства компилятора | Пользователь встречает разные границы analyze/IR/check/build и внутренние ошибки |

`Pin` одновременно обозначает аппаратный объект и в некоторых выражениях читаемый уровень. Выбранное в обсуждении направление `.level` стоит довести до согласованного контракта перед публичными драйверами, иначе они закрепят старую неоднозначность.

Запрет рекурсии, отсутствие heap и отсутствие полноценного ownership сами по себе не мешают первому прибору. Отсутствие буферов, состояния устройства, библиотечной композиции и периферийного доступа мешает непосредственно.

### Проверки и сопровождение

В checkout нет `.github` workflow. Полный набор сейчас зависит от ручного запуска и локально установленного toolchain. Нужны повторяемый CI хотя бы для host-тестов и отдельный обязательный машинный прогон перед выпуском; простая команда обычных тестов пропускает машинные проверки.

Интерпретатор и constant folder используют общую реализацию арифметики, поэтому их согласие не полностью независимо. Машинные тесты это частично компенсируют. Следующий прирост покрытия — комбинации возможностей и небольшие генерируемые программы с независимыми ожидаемыми результатами, а не только новые snapshots.

Библиотечный `check` не принимает CPU clock, CLI принимает. Это известное ограничение API, которое лучше убрать до LSP: у стадий должен быть общий объект конфигурации.

## Рекомендуемый вектор

### Этап 1. Зафиксировать надёжную основу

Исправить три дефекта выше, синхронизировать README, добавить регрессии. Включить verifier по умолчанию и для распространяемого компилятора хотя бы до первого стабильного выпуска: это средство обнаружения дефектов, не замена исправления семантики. Добавить автоматический host-прогон и явный machine-test gate.

Готово, когда результат проверки не зависит от debug/release и найденные случаи покрыты. Полезно сохранить текущий большой незакоммиченный срез отдельной понятной вехой перед следующим расширением; ревью само коммитов не создаёт.

### Этап 2. Подтвердить Timer1 и наблюдаемость на Nano

Проверить таймер на плате, загрузку, период, реакцию main во время ISR, поведение длительного запрета IRQ. Для следующей периферии первым полезным каналом будет минимальный UART-вывод: он позволит наблюдать датчик и ошибки раньше, чем появится меню LCD. Полный форматтер на этом этапе не обязателен.

Готово, когда есть повторяемый сценарий измерения, записанные результаты и понятная процедура сборки/прошивки для автора.

### Этап 3. Минимальная основа одного драйвера

Выбрать точную модель датчика и способ подключения. Из требований драйвера вывести небольшие итерации: i32/u32; битовые операции; определённые division/remainder; фиксированные массивы; структуры; минимальный import; согласованный Pin API. Порядок внутри этапа уточнять по прототипу драйвера. i64, generic ownership, heap и богатые строки не должны блокировать результат.

Если нужны ссылки на буферы — сначала ограниченные, не сохраняемые между вызовами заимствования с ясными правилами. Не обещать безопасность произвольных ссылок без реализации соответствующих проверок.

Для точных задержек потребуется аппаратный примитив и измерение машинного поведения. Обычный цикл с пустым телом не является надёжным API времени. Если весь драйвер на Helium пока чрезмерно дорог, небольшой явно изолированный аппаратный runtime — допустимый вариант для обсуждения; это изменение предпочтения, а не уже согласованное решение о C FFI.

### Этап 4. Один полный полезный прибор

Один датчик, один канал охлаждения, гистерезис, UART и обработка отсутствия/ошибки датчика; затем второй канал, энкодер и LCD. Ошибочное измерение не должно молча превращаться в обычную температуру. Для первого этапа допустим простой явный статус, без проектирования всей системы Option/Result.

Критерий: библиотека не привязана к одному глобальному имени пина, можно создать второй экземпляр, память ограничена, приложение выдерживает отключение датчика и длительный прогон. Пользователь собирает его из чистого checkout по инструкции.

### Этап 5. Проверка удобства независимым пользователем

Дать автору или отцу изменить пороги, подключить второй датчик и исправить несколько обычных ошибок, не заглядывая в Rust-код. Затруднения этого испытания определяют приоритет диагностики, документации и редактора. LSP полезен после стабилизации небольшого реально используемого языка.

## Оценка перспективы

Да, удобный язык для ограниченного круга хобби-проектов реалистичен. Текущая архитектура не выглядит тупиковой. Но нужен выбор: удобство нескольких законченных сценариев важнее количества распознаваемых конструкций и архитектурных гарантий «на будущее».

Если основная личная цель — только получить термостат с минимальными собственными затратами времени, разработка языка остаётся дополнительным проектом и не гарантирует кратчайший путь. Если интересен ещё и свой доступный инструмент для повторных домашних проектов, текущую основу имеет смысл доводить. Следующая инвестиция должна доказать этот смысл одним работающим прибором.
