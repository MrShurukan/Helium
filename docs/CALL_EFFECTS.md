# Контракты вызовов и compiler warnings

Принято и реализовано 27 октября 2026. Длительная обработка ISR сама по себе не
запрещена: потенциально блокирующий вызов получает **W_ISR_BLOCKING**. Операция,
прогресс которой требует разрешённых IRQ, в контексте запрещённых IRQ получает
**E_IRQ_REQUIREMENT**. Это разные свойства: время ожидания и условие прогресса.

## Представление

`intrinsics::Intrinsic` описывает встроенную операцию: имя, типы аргументов,
результат и `effects::Contract`. Контракт хранит IRQ requirement, возможность
блокировки и причину. Причина структурирована, допускает также статический текст
для будущих реализаций. Анализ эффектов не сравнивает имена UART-методов.

Методы устройства получают SymbolId и сигнатуру, но не искусственный AST функции.
Lowering создаёт `Op::Intrinsic { device, operation, arguments }`; verifier проверяет
устройство и типы, LLVM backend реализует аппаратную операцию. Встроенная реализация
может содержать LLVM helpers, не выдавая их за исходные функции Helium.

Обычные функции получают `Summary` по существующему графу вызовов. Небольшой анализ
до неподвижной точки распространяет блокировку и требование включённых IRQ, сохраняя
цепочку исходных вызовов. Метаданные можно привязать к любому SymbolId: независимые
unit tests добавляют контракт обычной функции Helium без UART. Пользовательского
синтаксиса для объявления произвольных эффектов пока нет; это не полная система эффектов.

Существующий `noInterrupt fn` остаётся явным требованием защиты вызывающего и
проверяется на каждом вызове. Для встроенной операции контракт Disabled преобразуется
в то же требование сигнатуры. Он не означает автоматическую вставку CLI в тело.

## Контексты и диагностика

- В ISR блокировка даёт warning на внешнем вызове, labels показывают путь через
  helpers. Для одного вызова показывается один свидетельствующий путь, не все пути.
- Сам по себе блокирующий контракт допустим в setup, loop, noInterrupt и ISR.
- Требование Enabled проходит через обычные helpers. Внутренний noInterrupt не
  снимает его: ошибка у проблемного вызова внутри защиты. Setup и ISR также закрыты
  для Enabled. Loop без включаемых lifecycle IRQ не удовлетворяет Enabled.
- Анализ синтаксически консервативен: учитывает все ветви и код после return.
  Он не доказывает длительность циклов, WCET, завершение произвольной функции или
  работоспособность конкретного внешнего устройства/источника IRQ.
- Проверка совместного доступа независима от эффектов. Разрешённая блокировка не
  отменяет требования защиты общего UART или общей памяти.

Polling UART имеет IRQ requirement Any. write_byte и flush отмечены blocking,
try_write_byte — нет. Контракт Enabled подготовлен и проверен синтетическими
тестами для будущих реализаций; IRQ-очередей или RX эта итерация не вводит.

## Возврат результата и CLI

`Diagnostic::severity()` отделяет warning от error. `AnalyzedProgram::warnings()`
и `Module::warnings` сохраняют исходные сообщения; `compile_llvm` возвращает
`Compilation { output, warnings }`, `check` — список warnings при успехе.
При ошибках результат остаётся Err с диагностикой.

CLI выводит сообщения в stderr, результат/артефакт остаётся доступным. Сборка,
содержащая только предупреждения, заканчивается успешно. Отключение предупреждений,
`allow`, `deny` и `-Werror` не реализованы. Текст, код, spans и severity доступны
независимо от терминального оформления.
