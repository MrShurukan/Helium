# Числовой контракт и этапы перед структурами

Согласовано 28 октября 2026. Этот документ отделяет исполняемый подэтап N1
от принятых направлений следующих подэтапов. Пользовательский `panic {}`,
float, usize/isize и обобщённые методы здесь не объявляются реализованными.

## N1 — целые числа, явное преобразование и общий аварийный останов

Поддерживаются i8/u8, i16/u16, i32/u32, i64/u64: анализ, Helium IR,
интерпретатор и LLVM AVR. Целые литералы получают тип из контекста,
без контекста — i32. Литерал должен помещаться в свой тип.

### Преобразования

`(T)expression` — явное числовое преобразование, с приоритетом унарной операции.
В N1 исполняется только целое → целое. Вычисление операнда происходит один раз.
Тип исходного выражения определяется независимо от целевого типа cast.
Например, `(u8)300` сначала получает исходный i32, затем оставляет младшие 8 бит.
Для литерала за пределами i32 требуется исходный контекст подходящего типа
(например, переменная u64); cast не делает произвольный литерал безразмерным.

Результат целочисленного cast определяется по модулю 2^N, где N — ширина
целевого типа. Знаковый результат использует дополнительный код:

```helium
var a:u8=(u8)300;       // 44
var b:u8=(u8)-1;        // 255
var c:i8=(i8)255;       // -1
var d:u16=(u16)c;       // 65535: расширение отрицательного значения
var x:u8=255;
var e:u16=(u16)(x+1);   // 0: сложение выполнено в u8
var f:u16=(u16)x+1;     // 256: сложение выполнено в u16
```

Cast не преобразует bool, PinState, устройства, массивы или ссылки и не
переинтерпретирует адреса. Неявные преобразования остаются без потерь для
всего диапазона исходного типа. Общий целый тип операции должен вмещать оба
диапазона: i16 + u16 → i32; i64 + u64 — ошибка, требуется явное решение автора.

IR различает `NumericCast` и неявный `Widen`: verifier запрещает использовать
Widen для сужения. Для будущих float-преобразований расширяется эта модель,
а не создаются отдельные операции для каждой пары числовых типов.

### Арифметика и биты

Реализованы `+ - * / %`, унарный минус, сравнения, `& | ^ ~`, `<< >>`.
Сложение, вычитание, умножение и отрицание используют циклическое переполнение
в ширине операции; поведение одинаково в debug/release. Унарный минус требует
знакового типа. Побитовые операции разрешены только для целых.

Деление округляется к нулю, остаток имеет знак делимого:
`-7 / 3 == -2`, `-7 % 3 == -1`. Нулевой делитель вызывает panic.
Для знаковых типов `MIN / -1` вызывает panic, `MIN % -1` возвращает 0.

Сдвиг сохраняет тип левого операнда; тип счётчика независим от него.
`<<` отбрасывает выходящие биты; `>>` заполняет нулями для unsigned и знаком
для signed. Счётчик обязан находиться в диапазоне 0..BITS-1. Проверка
выполняется до уменьшения ширины счётчика, поэтому u64-счётчик 256 для u8
не превращается в допустимый ноль.

Приоритет от низкого к высокому: присваивание, тернарный оператор, `or`, `and`,
`|`, `^`, `&`, равенство, сравнение, сдвиг, сложение, умножение/деление/остаток,
унарные операции/cast. Для масок в сравнениях используйте скобки:
`(flags & mask) == 0`. Префиксный `&` остаётся заимствованием.

Заведомо недопустимые константные делители и сдвиги диагностируются в исходнике,
в том числе после return. Проверка не является общим доказательством значений:
не доказанный статически случай проверяется при исполнении.

### Единый panic

В машинном коде проверки массива и числовых операций вызывают общий
`helium_panic(reason)`: отключение прерываний, затем бесконечный цикл.
Причины: Bounds=1, DivisionByZero=2, DivisionOverflow=3, InvalidShift=4.
Интерпретатор возвращает `Error::Panic(PanicReason)` с той же классификацией.
Пользовательского обработчика, восстановления исполнения и unwind пока нет.
Периферия автоматически не выключается, вывод в UART не гарантируется.

Деление, остаток и сдвиги с потенциальной panic не считаются чистыми операциями:
их нельзя удалить из-за неиспользуемого результата. Недопустимые входы не доходят
до LLVM-инструкций с неопределённым результатом/poison. Проверка сохраняет порядок
вычисления операндов и short-circuit. Успешные константные операции сворачиваются.

### Проверки и ограничение toolchain

`tests/numeric.rs` проверяет все ширины, знаки, cast, смешанные типы, границы,
диагностику и сохранение panic при оптимизации. `examples/uart-numeric.he`
проверяет целые операции и массив u64 через UART в AVR8js.
При LOW на PB0 ожидается `C12345678B`; при HIGH — `C`, затем останов на делении
на ноль. В тестах также есть отдельные машинные случаи MIN/-1, нулевого остатка,
широкого счётчика сдвига, MIN%-1 и расширения знака из i8/i16/i32.
Матрица: Helium IR optimization off/on × LLVM O0/O2/Oz × LOW/HIGH.
Итоговый полный gate: 245 debug + 245 release, fmt/Clippy, все machine tests.
Новые 5 числовых программ дают 60 AVR-сценариев в каждом профиле.
Лог: `build/numeric-full-gate-final.log`. После этого изменялась только документация.

Обнаружена ошибка поставляемого LLVM AVR: прямой `sext` в i64 при O0 может
читать неинициализированный регистр в сгенерированном SBC. Backend использует
изолированные helpers с приватной 8-байтной ячейкой на стеке и volatile-записями
знаковых/младших байтов. Они генерируются только при необходимости. Это обход
ошибки backend, не семантика языка; он увеличивает стоимость таких преобразований.
Его можно убрать после замены toolchain и прохождения тех же машинных регрессий.
Машинные проверки не означают прошивку физической платы или доказательство WCET/стека.

## Следующие подэтапы — до структур

### N2 — размеры целевой машины и usize/isize

Отдельные типы usize/isize, а не текстовые псевдонимы u16/i16. Для ATmega328P —
16 бит. Длины/индексы используют usize; длина строки измеряется в байтах,
массива — в элементах. Проверяется и полный размер объекта в байтах.
Ширина указателей каждого адресного пространства описывается отдельно:
usize не обещает вместить произвольный Flash-адрес другой AVR-модели.

Преобразования определяются диапазонами выбранной цели: на ATmega328P
usize ↔ u16 без потерь; usize → isize требует явного действия.
Добавить доступные программе BITS/MIN/MAX и вывод layout выбранной цели.
Точный синтаксис констант ещё согласовать. Проверить переносимость диагностики.

### N3 — f32, затем f64 и числовые cast с float

Контекст определяет тип дробного литерала, без контекста — f32.
f32/f64 сохраняют собственную двоичную точность; f64 не подменяется f32.
NaN, бесконечности, знаковый ноль; по умолчанию без fast-math.
Целые и float не смешиваются автоматически; f32 → f64 без потерь.
Явные целое → float и f64 → f32 могут округлять; переполнение float даёт
бесконечность. Float → целое усекает к нулю, проверяет результат и вызывает
panic для NaN, бесконечности или выхода за диапазон.
Проверить ABI программной арифметики, размер кода и машинное исполнение.

### N4 — общий resolver методов и дополнительные режимы преобразований

Общий узел вызова, проверенная сигнатура/receiver/эффекты, затем идентификатор
реализации. Не создавать цепочку специальных случаев для каждой пары типов.
Перенести Clone на этот путь; `r.clone()` должен означать `(*r).clone()`.
Контракты Copy/Clone и запрет дублирования эксклюзивного доступа сохраняются.
Проверяемые и насыщаемые преобразования используют общую модель конверсии.
`checked_to<T>()`/`saturating_to<T>()` — эскиз, не принятый синтаксис.
Проверяемый результат без panic зависит от будущих явных типов результата;
до структур согласовать контракт, исполнение вводить вместе с результатами.

### N5 — пользовательский аварийный обработчик

Проработать опциональный единственный `panic {}` с причиной и местом ошибки,
входом с отключёнными прерываниями и без возврата к ошибочной операции.
Конец блока и повторная panic ведут к стандартному останову. Определить доступ
к хранилищам при активных loans, вход из ISR/раннего setup, разрешённые выходы
и аварийный UART с ограниченным ожиданием, не зависящий от прерываний.
Не обещать возможность вызвать произвольную обычную функцию из обработчика.
Точный синтаксис и правила доступа требуют отдельного согласования.

После числового основания и согласования этих границ — структуры и явные
результаты/ошибки. Сохраняемые ссылки и lifetimes остаются отдельным направлением.
