# Roadmap: возможности, технический долг и принятые ограничения

Обновлено: 27 октября 2026. Цель — язык, на котором удобно сопровождать и развивать
реальный проект термостата. [DEVELOPMENT_PLAN.md](DEVELOPMENT_PLAN.md) задаёт порядок
ближайших работ; здесь хранится долгосрочный список и цена временных решений.
Фактическая поддержка описана в SUPPORT.md, состояние передачи работы — в HANDOFF.md.

## Как вести этот список

- Статусы: **обязательно**, **запланировано**, **исследование**, **идея**, **выполнено**.
  Обязательство означает необходимость завершить пункт, но не автоматическое разрешение
  включать его реализацию в любую текущую задачу. Срок задаётся зависимостью или этапом.
- При принятии временного решения сразу записывать: что оно позволило сделать,
  какое ограничение осталось, когда его нужно снять и чем подтвердить завершение.
- При завершении менять статус и добавлять результат/проверку; запись не удалять.
  Обновлять также DEVELOPMENT_PLAN и HANDOFF, если изменился следующий шаг или контракт.
- Идеи не считать согласованной семантикой языка. Отдельно отмечать машинные проверки,
  проверки на плате и предположения, ещё не подтверждённые измерениями.

## Обязательные архитектурные работы

| ID | Статус | Работа и условие завершения | Когда |
| --- | --- | --- | --- |
| R01 | Выполнено для ATmega328P | B2a: точные аппаратные эффекты и гарантированная атомарность. Различать чтение входа, запись бита, RMW, настройку и составные обращения. Независимые пины разрешать только при гарантированной реализации во всех режимах оптимизации; проверить машинный код и плату. | B2a: 130 тестов/профиль, 18 машинных комбинаций, 6 сборок на Nano; см. ATOMIC_GPIO.md |
| R02 | Обязательно | Передавать одно проверенное описание выбранного target во все стадии: source support, планировщик таймера, verifier, emitter, внешний toolchain и отчёты. Убрать самостоятельный выбор ATMEGA328P внутри стадий; не создавать второй путь компиляции. | До подключения внешних target и второго MCU |
| R03 | Обязательно | Загружать описания MCU из внешних файлов без пересборки Helium. Версия схемы, строгая проверка адресов/разрядностей/масок/делителей/векторов и ссылок на поддерживаемые модели периферии; понятные ошибки до генерации кода. Встроенное описание проходит тот же путь проверки. | После R02; до объявления поддержки MCU через конфигурационный файл |
| R04 | Обязательно | Поддержать несколько таймеров: идентификаторы и выбор ресурсов, конфигурации и ISR в IR, независимое резервирование, несколько векторов. Различия разрядности и способов настройки описывать явно; простой массив нынешних Timer1 недостаточен. | При расширении таймерного API, до заявления о нескольких таймерах |

Для R03 данные и поведение разделяются. Файл задаёт адреса, возможности и параметры
поддерживаемой модели. Порядок операций, W1C, правила многобайтового доступа и атомарность
имеют проверенную реализацию в компиляторе. Новое устройство добавляется только файлом,
если его периферия укладывается в эти модели и установленный LLVM/AVR toolchain его
поддерживает. Иное поведение требует расширения backend, а не произвольного сценария
из конфигурации. Формат файла пока не выбран.

Критерии проверки R02–R04: весь путь использует выбранное описание; неизвестные модели
и несовместимые конфигурации отвергаются; у нескольких таймеров нет взаимной перезаписи
регистров/ISR; эталонный ATmega328P сохраняет поведение. Второй MCU выбирается по реальному
проекту, не добавляется лишь для демонстрации универсальности.

## Реестр временных решений

| ID | Что позволило продвинуться | Оставшаяся цена | Как закрыть |
| --- | --- | --- | --- |
| D01 | B2 собрал аппаратные сведения в microcontroller.rs, сохранив текущий API. | Планировщик, TimerConfig и toolchain ещё обращаются к встроенному ATMEGA328P; загрузки target нет. B2 завершён как централизация данных, не как поддержка нескольких MCU. | R02, затем R03 |
| D02 | Один Timer1 CTC позволил реализовать и проверить полный цикл запуска/ISR. | В описании MCU, конфигурации и IR одиночный таймер/обработчик; форма регистров рассчитана на Timer1. | R04 |
| D03 | Правило целого порта позволило сначала защитить RMW без зависимости от оптимизации LLVM. | Закрыто B2a для текущего GPIO: SBI/CBI гарантируют независимость пинов. | Выполнено: R01 / B2a; для новых targets контракт обязателен |
| D04 | B1 использует один синтаксический граф вызовов для shared-анализа и volatile. | Вызовы после return и в константно ложных ветках учитываются; возможна излишняя консервативность. Обычный helper требует явного контракта — это текущее правило языка, не случайная ошибка. | Исследовать точность при реальных ложных отказах; менять контракты только отдельным решением |
| D05 | Машинный backend ограничен проверенными bool/PinState/i8/u8/i16/u16. | Более широкие типы в IR не означают поддержку их машинной сборки. | Добавлять ширины по потребностям драйверов с машинными тестами |
| D06 | AVR8js и полный test gate позволяют быстро проверять ISR и оптимизации. | Это не подтверждение электрического поведения, fuse/clock-конфигурации и времени на плате. B2a подтвердил GPIO/Timer1 smoke test на Nano; точность времени, джиттер и длительные испытания ещё не доказаны. | Частично выполнено: tools/board-gpio; продолжить длительные и электрические измерения |
| D07 | Отчёт flash/data/bss уже показывает размер статического размещения. | Стек и худшее время исполнения не доказаны; долгие критические секции могут терять отдельные события таймера. | B3 выполнен: отчёт и явное unknown. Для доказанной границы — D09 |
| D08 | Исходник BASIC позволяет выбрать реальные сценарии вместо синтетического термостата. | Нет исходной машинной сборки/листинга; размер, стек и аппаратное поведение не измерены. Исходник не включать в репозиторий. | Если понадобится численное сравнение с BASIC, получить артефакты и условия сборки. Для развития языка это не блокер; F12. |
| D09 | B3 сделал расход статической памяти и неизвестность стека явными. | LLVM .su не учитывает полный стек ISR; машинный граф вызовов, SP/CFG, startup/runtime и совмещение main/ISR пока не доказаны. Список вызовов относится ко всей функции, а не только маскированной области. | Отдельный анализ машинного стека с проверенными моделями; неподдерживаемые случаи остаются unknown. |
| D10 | Ёмкость MCU позволяет проверить итоговый ELF. | Резерв bootloader/профиль платы отсутствует; отчёт использует весь MCU. | До проверки пригодности для конкретной платы добавить доступные области и резерв bootloader. |

## Возможности и продуктовая проверка

| ID | Статус | Результат / следующий критерий |
| --- | --- | --- |
| F01 | Исследование | Исходник получен и разобран: три ЦКТ и общий контур, m168def.dat / 8 MHz. См. CKT_BASELINE.md. Референс возможностей, не задание на перенос логики; будущий проект будет написан заново пользователем с отцом. |
| F02 | Запланировано, следующий приоритет | Аппаратный UART для отладки на плате и в эмуляторе. Сначала согласовать границу native/std, владение аппаратным ресурсом и пользовательский API; затем реализовать и проверить. Конкретный синтаксис и объём TX/RX пока не утверждены. |
| F03 | Запланировано | По потребностям драйверов: битовые операции, division/remainder, i32/u32, фиксированные массивы, структуры, import, передаваемые пины. Каждая возможность получает отдельный контракт и тесты. |
| F04 | Запланировано | Библиотечные примеры: термометр, LCD, энкодер и обработка ошибок. На их разработке выбирать механизмы языка и контракты std; перенос алгоритма BASIC не требуется. |
| F05 | Запланировано | Проверить удобство самостоятельными изменениями отца: пороги, датчик, меню, исправления; по результатам определить приоритет редактора и диагностики. |
| F06 | Идея | Явное обращение к уровню пина через `.level`; синтаксис не согласован и не реализован. |
| F07 | Выполнено в границах B3 | ELF memory report, исследование стека с unknown, консервативная инвентаризация IRQ masking и вызовов. См. MEMORY_AND_TIMING.md; доказанная граница — D09, WCET не обещается. |
| F08 | Запланировано | Локализация пользовательского вывода компилятора: русский наряду с английским, с явным выбором языка. Перевести диагностики, подсказки, CLI help и отчёты; вынести оставшиеся строковые ошибки parser/scanner в каталог. Сохранить стабильные коды ошибок, исходные диапазоны и машинный формат независимо от языка; не переводить имена из исходника. Проверить одинаковую семантику и полноту сообщений для en/ru. Конкретный CLI-параметр согласовать при реализации; исходные сообщения внешних инструментов сохранять как есть. |
| F09 | Запланировано | Фиксированные массивы структур, обход и изменение элемента через функцию как средства библиотек и нескольких экземпляров устройств. Согласовать layout, индексы, alias и сохранение shared-гарантий до реализации. BASIC даёт примеры потребностей; синтаксис выбирать через библиотечные API. |
| F10 | Запланировано | Результаты датчиков: явные состояния, CRC, привязка ROM к роли, таймаут/устаревание. Политику исполнительных выходов при ошибках согласовать отдельно. |
| F11 | Запланировано | EEPROM: валидация/версия настроек, значения по умолчанию, сохранение изменений вне ISR. LCD: строки в Flash, небольшой целочисленный форматтер; кнопки и программные сроки без длинных ISR. |
| F12 | Исследование | Цена абстракций на AVR: один/три канала, массив против развёрнутого кода, индексация и проверки, копирование, форматирование. Измерять итоговые артефакты; паритет с BASIC требует его сборки и одинаковых сценариев. |
| F13 | Идея | Software UART после аппаратного. По возможности общий интерфейс передачи байтов, но отдельные контракты времени, CPU, пинов/таймеров и IRQ masking; не обещать одинаковые гарантии с hardware UART. |
| F14 | Обязательно, срок отдельно | Интерполяция строк для прикладного вывода, например "Temperature: $temperature". Синтаксис выражений/экранирования ещё согласовать. Проверка типов при компиляции, целочисленное форматирование библиотекой; предусмотреть потоковый вывод без heap и полной временной строки. Не ограничивать механизм UART. |

Heap, универсальные generics, ownership/lifetimes и множество targets не являются
условиями начала разработки библиотек. Их отсутствие не закрывается обещанием без конкретной задачи.

| --- | --- | --- |
| A1 | Выполнено | Явные lifecycle roles и отдельная инициализация; запуск ISR после setup. Машинные тесты ветвящихся инициализаторов. |
| A2 | Выполнено | Завершение типов и исходные проверки поддерживаемых форм, включая недостижимый код. |
| A3 | Выполнено | Verifier по умолчанию, configurable check, полный test gate и host CI workflow. Удалённый CI-прогон не заявляется проверенным. |
| B1 | Выполнено | AnalyzedProgram, разрешённые идентификаторы, общий shared-граф, отдельные setup/main/ISR; 123 теста в каждом профиле. |
| B2 | Выполнено | Единое описание GPIO/Timer1/SREG и параметров target. 126 тестов в каждом профиле; три контрольных HEX совпали побайтно. Ограничения D01/D02 сохраняются. |
| B2a | Выполнено | Атомарные GPIO-записи, точные конфликты пинов, объяснения защиты памяти; 130 тестов/профиль, реальная Nano и восстановление исходной flash. См. ATOMIC_GPIO.md. |
| B3 | Выполнено в согласованных границах | ELF memory report, проверка ёмкости, исследование стека и инвентаризация IRQ. 139 тестов/профиль; максимум стека unknown. См. MEMORY_AND_TIMING.md. |
| T01 | Выполнено | Направленный tolerance таймера: без знака — ближайший период с любой стороны, минус — не длиннее every, плюс — не короче. Точное совпадение разрешено всегда. Проверка направления в IR, диагностика отсутствующей стороны и тесты полного перебора. См. TIMERS.md. |

Оставшееся ограничение B2a: backend реализует GPIO-записи через low-I/O SBI/CBI.
Адреса без такой реализации отвергаются; для будущих targets нужно добавить
проверенную реализацию контракта, не возвращать незащищённый RMW (R02/R03).
Тестовая C-телеметрия не закрывает F02: публичного UART API языка ещё нет.

## Текущий приоритет

B3 выполнен в описанных границах. Далее — архитектурное overview перед hardware UART:
готовность к device/std, timer как отдельная конструкция или часть общей модели ресурсов,
контракты доступа/IRQ/lifecycle. Затем согласовать API UART. Маршрут — раздел 0 HANDOFF.md. Разработка std/библиотек должна выявлять полезные
механизмы языка; критерии — лаконичность, скорость, Flash/SRAM и безопасность.
BASIC — каталог возможностей, его нынешнюю логику не требуется моделировать или
переносить. Приложение пользователь с отцом планируют писать заново. R02–R04 сохраняются.
