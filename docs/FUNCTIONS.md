# Функции Helium

Реализован путь `fn` → AST → Helium IR → LLVM AVR → HEX.
LLVM — единственный backend машинного кода.

```text
fn add(left:u8, right:u8):u8 {
    return left + right;
}

fn set_led(enabled:bool) {
    if enabled {
        Led = HIGH;
    } else {
        Led = LOW;
    }
}
```

## Контракт языка

- Ключевое слово — `fn`. Старое `fun` зарезервировано, но не является синонимом.
- Функции объявляются только на верхнем уровне, в том числе между setup/loop и после loop.
  Глобальные переменные и пины по-прежнему должны предшествовать setup/loop.
- Сначала собираются все сигнатуры: вызов функции, объявленной ниже, разрешён.
  Тела функций видят все глобальные объявления, независимо от своего положения в файле.
- Параметры явно типизированы. Допустимы целые числа, bool и PinState.
  IR поддерживает 8/16/32/64 бит; LLVM AVR пока принимает только 8/16 бит.
  Float, string, PinMode и ссылки на физические пины в сигнатурах не поддерживаются.
- Результат записывается через `: тип`. Отсутствие типа означает отсутствие результата;
  слова `void` и вывода типов сигнатур в исходном языке нет.
- Параметры — изменяемые локальные копии значений. Присваивание параметру не меняет переменную
  вызывающего кода. Аргументы вычисляются слева направо; каждое значение фиксируется до следующего.
- Для аргументов и результатов действуют прежние правила: проверка диапазона литералов,
  расширения без потери значений, без неявного сужения и преобразования bool в число.
- `return выражение;` возвращает значение; `return;` завершает процедуру.
  Неявного возврата последнего выражения нет. В setup/loop `return` запрещён.
- Процедура вызывается отдельным оператором `f();`. Результат обычной функции можно
  использовать в выражении или проигнорировать таким же оператором.
- Затенение запрещено. Параметры и локальные имена не могут совпадать с видимыми глобальными
  именами, пинами, функциями или параметрами. Разные функции могут иметь одноимённые параметры.
- Вызовы в глобальных инициализаторах запрещены: их нужно переносить в setup, который
  выполняется после инициализации глобальных данных и режимов пинов.
- Нет вложенных функций, значений-функций, перегрузок, аргументов по умолчанию и завершающих запятых.

## Возвраты и рекурсия

Проверка возвратов консервативна и не зависит от оптимизаций: `return` завершает путь;
`if/else` завершает его, если обе ветви возвращают значение. Цикл сам по себе этого
не доказывает — даже после `while true` требуется явный return в функции с результатом.

Код после return проверяется на имена, типы и рекурсию, но не порождает инструкции IR.
При завершении обеих ветвей не создаётся открытый блок с фиктивным результатом.
Частичный ранний возврат сохраняет продолжение только для незавершённой ветви.

Прямая и косвенная рекурсия отклоняются, в том числе в неиспользуемых функциях и недостижимом коде.
Диагностика показывает цикл вызовов, например `read -> retry -> read`, и место замыкающего вызова.

Новые категории: `E_CALL`, `E_RETURN`, `E_RECURSION`. Общий renderer сохраняет исходные spans
и раскраску; неизвестные имена, дубликаты, диапазоны и преобразования имеют прежние категории.
Тексты находятся в общем каталоге для будущей локализации.

## IR, стек и память

FunctionId пользователя начинаются с f3 и следуют порядку исходных объявлений; f0/f1/f2 —
entry/setup/loop. Параметры — входные значения IR, сохранённые в локальные слоты для присваивания.
LLVM может устранить слоты, использовать регистры, стек или встроить функцию.
Порядок аппаратных эффектов и контракт циклической арифметики не меняются.

Стартовый код и LLVM обслуживают аппаратный стек. Heap и allocator не добавлены.
Нет проверки переполнения стека или доказанного максимума памяти всей программы.
Запрет рекурсии упрощает будущую оценку, но сам по себе не гарантирует достаточность стека.
ISR, публичный C ABI и FFI остаются вне этой итерации.

## Примеры и проверка

- `examples/functions-thermostat.he`: гистерезис с температурами в десятых долях градуса.
  При равенстве порогу состояние сохраняется. Это логика с искусственными входами, не драйвер датчика.
- `examples/functions-latch.he`: Nano, встроенный LED D13, кнопка D2–GND и INPUT_PULLUP.
  Использует функции, параметр bool и ранние возвраты. Подавления дребезга пока нет.

```powershell
. ./tools/activate-toolchain.ps1
cargo build --locked --release
./target/release/helium.exe check examples/functions-latch.he --mcu atmega328p
./target/release/helium.exe build examples/functions-latch.he --mcu atmega328p --opt size -o build/functions-latch.hex
```

Эти команды не прошивают плату. Пользователь подтвердил работу прежнего latch на Nano;
новый вариант с функциями пока прошёл эмулятор и требует отдельного аппаратного прогона.

В итерации добавления функций были проверены **72 теста в debug и release**, включая **45 сборок HEX и запусков AVR8js на профиль**.
Новые тесты покрывают forward calls, изменяемые копии параметров, расширение результатов,
ранние возвраты, порядок эффектов, рекурсию, ошибочные сигнатуры и обрезанные префиксы программы.
Семантика проверяется до и после экспериментальных оптимизаций Helium IR.

Пять новых машинных сценариев проходят none/speed/size: термостат, latch с пятью опросами кнопки,
вложенные вызовы с 12 параметрами i16, эффекты вызовов и ранние возвраты. Глобальные данные,
GPIO-эффекты и DDR сравниваются с интерпретатором. Тестовый `noinline` сохраняет реальные вызовы
пользовательских функций; дизассемблирование дополнительно подтверждает вызов f3.

У 12-параметрического сценария наблюдалось 102 байта стека без оптимизации, 26 в speed и 30 в size.
Это максимум конкретного выполнения с тестовым noinline, не гарантия для произвольной прошивки.

Полный прогон: `cargo test --locked -- --include-ignored`, затем то же с `--release`.
Внешние тесты требуют активированного LLVM/AVR toolchain, Node/AVR8js.
Обычный `cargo test` оставляет три внешних теста явно пропущенными.
